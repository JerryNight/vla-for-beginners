    3.2 融合：三股信息在哪里合流¶

    对齐解决了「能比」，融合解决「怎么用」¶

    上一节讲 CLIP，解决的是「图和文能不能放在一起比较」。

    但 VLA 要做的不止是比较。它要把图、文、以及机器人自身状态，合成一个足够做出决策的东西。

    这个「合成」的动作，叫融合（fusion）。

    融合发生在哪一层，决定了整个模型的性格。这是看架构图时最该先认出来的东西。

    三种融合方式¶

    ① 早期融合（early fusion）¶

    做法：把视觉 token、语言 token、本体 token 拼成一个长序列，一起送进同一个 Transformer。从第一层开始，它们就能互相看见。

    [图块1][图块2]...[图块196][指令词1][指令词2]...[关节1][关节2][动作1][动作2]...
└──────────────── 一个序列，一起过 Transformer ────────────────┘

    代表：RT-2、OpenVLA、几乎全部基于 LLM 主干的 VLA。

    为什么成了主流

    因为主干本来就是语言模型。语言模型只认序列，那最自然的做法就是把别的模态也变成 token 塞进去。

    改造成本几乎为零——不用改架构，只需要加一个「投影层」把视觉特征映射到语言模型的维度上。

    优点

    • 模态之间可以任意深度地交互。视觉 token 和语言 token 在第 1 层就能互相注意，不需要设计专门的接口；
    • 能复用语言模型已有的能力（常识、推理、指令跟随）；
    • 结构简单，就是「拼序列 → 过模型」。

    缺点

    • 序列变长。视觉 196 个 + 语言 20 个 + 动作若干，上下文很快吃满（2.1 节算过这笔账）；
    • 模态失衡。视觉 token 数量是语言的十倍，注意力会被视觉主导，指令里那个关键的「红色」可能被淹没；
    • 位置编码要特殊处理——图像块的位置和词的位置不是一回事。

    模态失衡是个真问题

    有研究发现，在早期融合的 VLA 里，输入指令对最终动作的影响比预期小得多。 换句话说：你让它「拿左边的」，它可能只听懂了「拿」，左右没进去。

    缓解办法有几种：给语言 token 加权、把指令放在序列末尾（离动作输出最近）、 或者干脆在训练时随机替换指令做「反事实数据增强」。

    ② 晚期融合（late fusion）¶

    做法：图、文各自过自己的编码器，得到两个向量，然后在特征层拼接（concatenate）或者相加，再送进一个小网络（MLP）输出动作。

    图 → 视觉编码器 → 向量 ┐
                       ├→ 拼接 → MLP → 动作
文 → 文本编码器 → 向量 ┘

    代表：早期的一批工作，以及一些轻量级方案。

    优点

    • 每个模态可以用最适合自己的编码器，不用迁就；
    • 计算量小，两个编码器可以并行；
    • 结构清晰，好调试。

    缺点

    • 交互太浅。两个向量拼起来之后才第一次相遇，信息已经压缩过了，细节丢了；
    • 不适合需要细粒度对齐的任务。比如「抓杯子的把手」——「把手」这个词需要和图上那一小块区域精确对应，晚期融合做不到。

    类比

    早期融合：所有人在同一张桌子上开会，随时可以插话、互相纠正。

    晚期融合：各部门先各自开完会，各派一个代表，最后代表们碰一次头，汇总成结论。

    前者信息更充分但容易乱；后者高效但细节全在部门内部消化掉了。

    ③ 交叉注意力（cross-attention）¶

    做法：一个模态作为「查询方」（query），去主动检索另一个模态的信息。

    最典型的用法：动作作为 query，去 attend 视觉和语言特征。

    动作 query ──→ [交叉注意力] ←── 视觉特征 / 语言特征
                    ↓
                  动作

    代表：很多基于扩散策略的 VLA、以及一些非 LLM 主干的架构。

    优点

    • 定向检索。不是「所有信息混在一起」，而是「我需要什么就去取什么」；
    • 计算效率高。query 的数量（比如 16 个动作 token）远小于视觉 token 数，注意力矩阵小；
    • 天然支持多模态输入，加一路触觉、加一路深度图，都不用改结构。

    缺点

    • 需要设计「谁 query 谁」，是个架构选择；
    • 如果 query 本身信息不足（比如动作还是初始噪声），检索效果会打折——这也是为什么扩散模型里通常要做多轮。

    三种方式放在一起比¶

    早期融合 晚期融合 交叉注意力
    融合发生在 第一层 最后一层 中间，按需
    模态交互深度 最深 最浅 中等，可控
    序列长度 长 短 短
    实现复杂度 低（拼序列） 低 中
    适合场景 基于 LLM 主干 轻量、实时 需要定向检索
    典型代表 RT-2、OpenVLA 早期方案 扩散策略类

    一句话记忆：

    • 早期融合 = 一开始就混在一起
    • 晚期融合 = 各干各的，最后汇总
    • 交叉注意力 = 谁需要谁去拿

    为什么 2024 年之后几乎全是早期融合¶

    三个原因，按重要性排：

    1. 语言的先验太值钱

    一个预训练好的 7B 语言模型，带着整个互联网的常识。你想用上它，最省事的办法就是让它来处理你的 token。

    晚期融合用不上这个——语言编码器只是把句子变成一个向量，语言模型的深层能力完全浪费了。

    2. 架构统一带来的工程红利

    早期融合不需要为每个模态设计专用模块。加一路相机？多塞 196 个 token。加触觉？再塞几十个。

    整个系统的复杂度是「线性增长」的，而不是每加一个模态就要重新设计一遍融合逻辑。

    3. 缩放定律的诱惑

    语言模型的经验是：参数越多、数据越多，效果越好。

    早期融合让 VLA 可以直接继承这条曲线——把主干从 3B 换到 7B 换到 70B，其他都不用改。

    但这条路的代价正在显现

    早期融合把「序列长度」变成了核心瓶颈。

    视觉 token 占了绝大部分上下文，而动作输出需要的精度却是最高的。 这个矛盾在6.1 节会展开——它是当前 VLA 推理速度上不去的根本原因之一。

    一个具体的实现细节：投影层¶

    不管你选哪种融合，中间都有一步躲不掉：维度对齐。

    视觉编码器输出的维度（比如 1024）和语言模型的维度（比如 4096）通常不一样。所以中间要加一个线性层：

    # 概念示意
vision_feat = vision_encoder(image)        # [196, 1024]
vision_tokens = projection(vision_feat)    # [196, 4096] ← 一个线性层
seq = concat([vision_tokens, text_tokens]) # [216, 4096]
out = llm(seq)

    这个 projection 就是架构图里那个常被画成小方块的 Linear 或 MLP projector。

    它看起来微不足道，但训练时很关键：如果它初始化得不好，视觉信息在第一步就被破坏了，后面的 LLM 再强也救不回来。

    有些工作会专门为这个投影层设计多阶段训练——先冻结 LLM 只训投影层，再联合微调。目的就是让这个「翻译官」先学会说人话。

    还有第四种：不加融合¶

    有一个思路值得单独提一句，因为它反直觉。

    为什么不把图像编码成 token，而是把它编码成一个「软提示」（soft prompt）？

    也就是：用一个小网络（比如 Q-Former、Perceiver Resampler）把 196 个视觉 token 压缩成 8 个或 16 个，再送进 LLM。

    好处是上下文占用直接降一个数量级。

    坏处是信息有损——196 个 token 压成 8 个，细节肯定丢。

    这个取舍在实际系统里很常见：如果你只需要「大致知道场景里有什么」，压缩划算；如果你需要「精确抓取某个位置」，最好别压。

    本章小结¶

    融合方式决定了模型的三种性格：

    • 早期融合给的是「深度交互 + 语言先验」，代价是长序列和模态失衡；
    • 晚期融合给的是「轻量高效」，代价是交互太浅；
    • 交叉注意力给的是「定向检索」，代价是要设计好谁问谁。

    2024 年之后主流选早期融合，不是因为它在所有维度都最优，而是因为它最能吃到预训练语言模型的红利。

    自测三问

    1. 早期融合和晚期融合，最本质的区别是什么？为什么晚期融合做不了「抓杯子的把手」这种任务？
    2. 什么是「模态失衡」？它会导致什么现象？有哪几种缓解办法？
    3. 为什么 2024 年后的 VLA 几乎都用早期融合？说出两个理由，并说明各自付出了什么代价。

    融合分三层：早期（拼序列，最深）、晚期（拼特征，最浅）、交叉注意力（按需检索）。 主流选早期融合，是为了吃到语言模型的预训练红利，代价是长序列与模态失衡。
