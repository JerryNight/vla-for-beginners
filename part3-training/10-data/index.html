    4.1 数据：一条机器人训练数据长什么样¶

    前面三部分讲的是「模型怎么工作」。从这一章开始讲「模型怎么学」。

    而学习的第一件事，永远是数据长什么样。

    一条数据的结构¶

    在 VLA 里，一条训练样本叫一个 episode（回合 / 轨迹）。

    它不是什么神秘的东西，就是一个 JSON 结构：

    {
  "language": "把红杯子放到盘子上",
  "frames": [
    {
      "images": {
        "third_view": "...",   // 第三人称相机，640×480
        "wrist":      "..."    // 手腕相机，640×480
      },
      "state":  [0.12, -0.34, 0.88, 0.02, 1.57, 0.0, 0.85],  // 关节角 + 夹爪
      "action": [0.002, -0.001, 0.010, 0.0, 0.0, 0.03, 1.0]   // 7 维动作
    },
    { ... }   // 下一帧
  ]
}

    就这么三个字段反复出现：

    字段 是什么 谁提供
    images 相机拍到的画面 相机
    state 机器人自己的状态 编码器（关节角）
    action 这一帧应该做什么 人手操作的记录

    注意最后一列。 这是 VLA 数据最特殊的部分：标签是人的动作，不是人给的答案。

    文本数据里，标签是人写的。图像分类数据里，标签是人标的。而机器人数据里，标签是人亲自做了一遍，机器记录下来的。

    这件事决定了机器人数据的全部特性：贵、慢、少、且带人的毛病。

    怎么采集：遥操作¶

    绝大多数机器人数据靠遥操作（teleoperation）采集。

    具体做法有几种：

    方式 怎么做 优点 缺点
    主从臂 操作员握住一个「主臂」，从臂跟着动 力反馈真实，精度高 设备贵（一套几万到几十万）
    VR 手柄 戴 VR 头显，用手柄控制末端 便宜，直观 没有力觉，精细操作差
    空间鼠标 用 3D 鼠标控制末端 设备最便宜 学习曲线陡，动作不自然
    动捕手套 手部动作捕捉，映射到灵巧手 适合多指操作 校准麻烦

    不管用哪种，流程都是：

    操作员做一遍 → 相机录下画面 → 编码器记录关节角 → 系统反算出末端位姿 → 存成 action

    那个「反算」很关键。操作员控制的是末端（或主臂），但底层记录的动作通常是末端位姿的变化量，这需要正运动学把关节角换算过去。

    这里就埋下了第一个数据质量隐患：正运动学和相机标定都有误差，而这两个误差会直接进到标签里。

    规模：差了几个数量级¶

    这是理解 VLA 现状最关键的一张表。

    数据类型 大致规模 采集成本
    纯文本 \(10^{13}\) tokens 爬虫，几乎免费
    图文对 \(10^{9}\) 对 爬虫 + 过滤，很便宜
    机器人轨迹 \(10^{6}\) 条 每条 10–30 秒的人工操作

    换算一下：

    • 一个熟练操作员，一小时能采 100–200 条轨迹；
    • 采 1 万条，需要 50–100 小时（约两周全职）；
    • 采 100 万条，需要 5000–10000 小时——一个人要干三年。

    而 100 万条，只是文本数据的百万分之一量级。

    这个差距不是「再等等就好了」

    文本数据是人在上网时顺手产生的副产品，边际成本接近零。

    机器人数据必须专门雇人去做，每一秒都是成本。这个差别不会因为技术进步而消失， 它只会被缓解（比如用仿真、用人类视频），不会被抹平。

    这就是第 6.1 节说的「数据是硬约束」。

    开源数据集长什么样¶

    几个你一定会遇到的名字：

    数据集 规模 特点
    Open X-Embodiment 100 万+ 轨迹，22 种机器人 多机构联合，格式统一，是跨本体研究的基础
    DROID 7.6 万条，13 个机构 场景多样（真实家庭、办公室），标注质量高
    BridgeData 数万条 早期重要数据集，厨房场景为主
    RT-1 数据 13 万条，700+ 任务 Google 内部采集，未完全开源
    LeRobot 数据集 数千到数万 HuggingFace 生态，格式最友好，适合入门

    格式上有两个主流：

    • RLDS（Reinforcement Learning Datasets）：基于 TensorFlow Datasets，Open X-Embodiment 用的就是这个。特点是能把不同机器人、不同任务的数据统一成同一种结构，方便混合训练。
    • LeRobot Dataset：基于 Parquet + MP4，视频单独存，元数据在表格里。如果你要动手，从这个开始最省事（见附录）。

    数据质量的五个坑¶

    这一节是实践中最有价值的部分，但很少有教程写。

    坑一：人的手在抖¶

    操作员不是机器人，手会抖、会犹豫、会中途停顿。

    这些抖动被如实记录进了 action 标签里。

    结果：模型学到的动作也带抖动，执行起来一顿一顿。

    缓解办法：对动作序列做平滑滤波（比如 Savitzky-Golay），或者用动作块（一次预测多步，天然平滑）。

    坑二：动作和画面对不齐¶

    相机有延迟，编码器有延迟，两者还不同。

    如果第 t 帧的画面配的是第 t+2 帧的动作，模型就会学到「看到 A 做 B」这种错位映射。

    这种错误肉眼看不出来，但会显著拉低性能。 检查方法：录一段快速移动的轨迹，看画面里的运动和记录的动作是否同步。

    坑三：不同操作员的风格差异¶

    A 操作员习惯从上方抓，B 习惯从侧面抓。

    这既是问题（数据不一致，模型学到平均行为）也是好事（多样性让模型知道多种做法都行）。

    关键看任务：如果任务要求精确复现，需要统一风格；如果要求泛化，多样性是资产。

    坑四：失败的轨迹要不要留¶

    采集时总会遇到抓空、撞到、走错路。

    这些数据里，action 标签是「错误的操作」。如果直接拿来训练，模型会学会犯错。

    但如果全扔掉，模型就没见过「出错之后怎么补救」。

    主流做法：失败轨迹保留，但用「成功/失败」标签区分，训练时降权或者只在特定阶段使用。

    坑五：语言标注的质量¶

    「把杯子拿过来」——哪个杯子？拿过来放哪？

    很多数据集的指令是事后补的，标注员看图写一句话，往往写得含糊。

    指令的含糊程度，直接决定了模型对语言的理解能力。

    有些项目会做「指令增强」：给同一条轨迹配十种不同说法（「拿杯子」「把红色那个给我」「我渴了」），强行让模型学会忽略措辞差异、抓住语义。

    数据增强：一半有用，一半有害¶

    这是机器人数据和图像数据最大的不同，值得单独说。

    在图像分类里，你可以随便做数据增强：翻转、裁剪、旋转、变色。因为「这是猫」这个标签不受影响。

    在机器人里不行。因为动作和像素位置是绑定的。

    增强方式 对图像分类 对 VLA
    颜色抖动 有用 有用（提升光照鲁棒性，动作不变）
    随机亮度/对比度 有用 有用
    随机裁剪 有用 有害——「往左 2 厘米」对不上了
    水平翻转 有用 有害——左右手的动作全反了
    随机旋转 有用 有害——「上方」不再是上方
    加高斯噪声 有用 轻微有用（模拟传感器噪声）

    规律很清楚：只改变「外观」的增强可以用，改变「几何关系」的增强不能用。

    一个例外

    如果你同时把动作也做对应的几何变换（比如图像水平翻转，动作的 y 分量也取反）， 那翻转就是合法的。

    但这件事做起来很麻烦，而且容易出错，所以实践中很少有人这么干。 大家更愿意用「换背景」「换光照」「换桌面纹理」这类只改外观的方式。

    一句话总结这章¶

    一条机器人数据 = 一段视频 + 一句指令 + 一串人的动作。

    它的贵，不在存储，在那个「串人的动作」——每一秒都要有人真的做一遍。

    它的难，不在规模，在那个「人的动作」——带抖动、带延迟、带风格差异、带失败。

    自测三问

    1. 一条 episode 里有哪三个关键字段？其中哪个是「标签」，它和其他机器学习任务的标签有什么本质不同？
    2. 为什么机器人的数据增强不能像图像分类那样随便翻转、裁剪？举一个具体的失效例子。
    3. 一个操作员一天能采多少条数据？这个数字和文本数据的规模差多少个数量级？

    机器人数据的标签是「人真的做了一遍」的动作，这决定了它贵、慢、少，且带着人的全部毛病。 增强只能改外观，不能改几何——因为动作和像素位置是绑死的。
